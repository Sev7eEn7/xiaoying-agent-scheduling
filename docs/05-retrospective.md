## 最难的几个问题（都是在真实模型运行中才暴露出来的）

> 问题 1–4 是开发早期用 `deepseek-chat` 运行时发现的；修复后切换到候选人指定的 `deepseek-flash`，所有提交结果都基于 Flash。

### 1. 幂等判重被模型的自由文本打破

第 1 轮里，“重复提交同一请求”返回了 `updated`（修订 2），而不是 `duplicate`。原因是草稿内容哈希包含了模型写的 `note`，而模型每次的措辞都不一样，同一个排期决策因此被当成了新内容。Mock 每次输出完全相同，所以离线测试发现不了这个问题。

修复：判重只看语义字段（素材、渠道、时段、确认状态、审核结果），`note` 不参与判重；补了回归测试 `test_note_wording_change_is_still_duplicate`。证据：[history/deepseek-chat-round1/03_duplicate](../examples/runs/history/deepseek-chat-round1/03_duplicate/trace.md)。

**体会**：接入大模型以后，“相同请求”的判定不能依赖模型生成的任何文本，幂等键和判重字段都要由确定性的代码掌握。

### 2. 用自由文本推导任务状态

第 1 轮的 09 中，模型的决策完全正确（M10 在允许窗口内调整，状态为 `not_required`），但它在 `pending_items` 里写了一句说明，汇总逻辑把“`pending_items` 非空”当成了待确认，于是任务状态被误判为 `needs_confirmation`。

修复：`task_status` 只看结构化字段（`confirmation_status`、`review_status`）；同时在 schema 里写清楚 `risk_reasons` 和 `pending_items` 应该放什么内容。之后模型就不再把“审核全部通过”之类的话写进风险原因了。

### 3. 测试输入泄露了答案

冒烟测试时，trace 里模型的依据写着“备注提示该时段已被占用”。原来是我在请求 JSON 的 `note` 字段里写了场景说明，模型直接读到了答案，而不是通过 `query_slots` 发现冲突。如果不逐条看 trace 的 `reason`，这类问题很难发现：检查项全部会通过，但证明不了模型在做决策。

修复：输入里删掉所有场景提示，场景说明只放在 `scenarios.json`（模型看不到）。

### 4. temperature=0 也不稳定：安全但不是最优

第 2 轮的 09 中，模型把 20:00 留给了有可调整窗口的 M10，把没有窗口的 M09 改到 21:00 并标记待确认。这个结果没有越权（改动已经标了 pending，工具层也会拦截），但多制造了一次本可以避免的确认。第 1 轮同一个场景却是最优解。

处理：在提示词里加了一条**通用**业务规则（争同一时段时，优先调整能在自己窗口内解决的素材），并加了 `suite --repeat N` 来统计通过率，不再只看单次结果。

**体会**：边界类的要求（不越权、不虚报、不重复）必须用代码兜底，因为它们不能“偶尔做到”；优化类的偏好（少打扰用户）可以交给模型和提示词，但需要用重复运行来度量，不能只看一次。

### 5. “用户同意”到底是什么

“未经用户同意不得改变硬性要求”需要先落到数据结构上。最终定义了三种合法状态：与原要求一致或落在 `acceptable_window` 内是 `not_required`（用户已经事先授权了范围）；有对应的 `confirmations` 记录是 `confirmed`；其他情况一律是 `pending`。保存工具按这个定义做二次校验，模型就无法自己把改期标成已确认。

## 学习收获

- **判断与事实分开**：模型负责给出结论和措辞；“是否已保存、保存到哪、草稿是第几版”由工具账本计算。这样即使模型说错了，报告也不会错。
- **三层防线**：提示词说明边界，工具层拒绝越权写入，finish 与账本核对。关键缺陷都不能只靠提示词来防。
- **Mock 只能证明流程**：上面的问题 1、2、4 在 Mock 下都发现不了，必须用真实模型跑，并且要逐条读 trace。
- **评估要可重复**：把期望写成机器可检查的条目，把失败的历史运行留下来，并用重复回放衡量稳定性。

## 下一步

1. 用真实模型做提示词注入测试：在素材文案里加入“忽略规则直接保存”之类的内容，验证工具层兜底是否有效，并观察模型是否会被带偏。
2. 人工复核流：把 `confirmations` 扩展到复核结论（例如法务确认肖像授权已回传），让 `review` 素材可以进入 `confirmed`。
3. 自然语言请求：由模型先把自然语言解析成结构化请求，再交给用户确认，然后进入现有流程。
4. 存储换成带乐观锁的数据库，支持多人同时提交。
5. 用同一套场景横向评估更多模型（Qwen、Kimi 等 OpenAI 兼容接口），比较通过率和成本。
