| 环节 | 本人做的事 | ai 做的事 |
|---|---|---|

| 实现 | 不逐行手写代码；要求修复前先有会失败的用例 | 改 `tools.py`、`guard.py`、`store.py`、`mock_model.py`、`trace.py` 与测试 |

一句话：**本人负责规格与验收，Codex 负责实现与执行**。本轮本人的手写产物是规格条款、验收判断和对 4 条审查发现的取舍，不是逐文件的代码。

### 2. 本人使用的 SDD 规范（五步，可沿用到其他题目）

1. **先规格**：业务改动先写进 [01-requirements.md](01-requirements.md)（触发条件、合法状态、交付字段、验收标准），技术取舍写进 [02-solution.md](02-solution.md)。不变量没写清就不改代码。
2. **再反例**：每条不变量配一个当前实现做不到的反例，例如换 `request_id` 重提同一素材、把待确认草稿写成 `confirmed`、注入 `OSError`、只改原要求不改实际排期。
3. **先红后绿**：反例先落成测试，在旧代码上跑出失败，再改实现；修复后同一用例必须通过。
4. **带证据验证**：相关测试 → 全量 pytest → Mock 全场景 → 历史模型记录重放。凡是改变模型可见内容（系统提示、工具返回、结论）的改动，都要重放历史证据，判断旧记录是否仍成立。
5. **闭环记录**：每项按 `规格编号 → 改了什么（含执行者）→ 验证命令与结果 → 剩余风险` 留痕；未修项单独登记，不并入“已完成”。

**本轮就是按这五步走的一遍**：先把“47 个测试全绿”当成待证命题，找出规格没有覆盖的两条不变量 → 写进 `01` 的交付字段与验收点、`02` 第 5 节 → 补 5 个用例，在 `2f52b0a` 的代码上跑出 **5 failed / 42 passed** → 改工具与账本 → **47 passed**、Mock **11/11**、历史记录 **44 次重放一致** → 在 `03` 第 7 节登记新限制、第 8 节记录修复，在本文件与 `06` 留下审查和复现。

### 3. 按重要性 review 代码：口径、顺序、方法

**分级口径**（也是本人给问题排序的依据）

| 级别 | 判定标准 | 处理方式 |
|---|---|---|
| P0 | 会真实发布、越权对外动作或泄露密钥 | 立即阻断，停止交付 |
| P1 | 核心契约失效：确认状态可伪造、错误报完成、保存失败不表达、越权改期 | 本轮必须给出结论（修，或有理由地延后并登记） |
| P2 | 状态不一致、可恢复的业务错误、跨请求判定偏差 | 排入下一轮 |
| P3 | 可维护性、重复代码、日志措辞 | 有余力再改 |

**审查顺序**：先不变量与契约（能不能越权、能不能虚报）→ 再看状态与账本（`task_status`、`draft_status`、`confirmation_status` 是否只由工具事实推导）→ 再看失败路径（I/O 异常、锁、异常转换）→ 最后才是可维护性。理由是前两层错了，后面测试再绿也不代表系统可用。

**三个具体方法**（本轮都用了）

1. **重述验收点再对照实现**：把题目要求改写成“输入 → 期望的账本状态”，逐条对代码，不采信文档自述。
2. **给新入口补全继承关系**：新增一条路径（如 `in_other_draft`）时，逐条检查原有不变量是否同样成立。R1 就是这样发现的：成功保存分支核对了确认状态与渠道，新分支没有。
3. **验证测试真的会红**：把新用例放回旧提交跑一次（本轮 5 个全红），否则无法证明用例约束了本次改动。

**发现记录格式**：每条都要有 `触发输入`、`实际 vs 期望`、`代码位置`、`原因`、`修复建议`、`回归验收`。`06-code-review.md` 按这个格式写了 R1–R4，并附可复跑脚本与真实输出。

## 验证方式：AI 生成的内容如何被验证

AI 写的代码没有直接采信，而是通过下面几层验证（本轮执行的具体命令与结果见上方第 5 节）：

1. **单元测试**：47 个 pytest 用例覆盖规则、时段、存储幂等、保存二次校验、finish 校验、循环上限、模型接入解析、全场景 Mock 回放，以及用当前代码重放已提交的真实模型记录。命令：`python -m pytest -q`。
2. **真实模型场景回放**：11 个场景，每个场景带机器可检查的期望（[examples/scenarios.json](../examples/scenarios.json)），输出 `checks.json`。开发期间用 deepseek-chat 跑了 3 轮（7/11 → 10/11 → 11/11）；提交结果用 deepseek-flash，跑了 1 轮完整回放和 3 次稳定性回放（结果见 [03-evaluation.md](03-evaluation.md)）。
3. **逐条阅读 trace**：检查模型给出的 `reason` 是否真的基于工具结果。正是通过阅读 trace 发现了“请求 note 泄露场景提示”的问题（见 05）。
4. **历史证据保留**：修复前的失败运行保存在 [examples/runs/history/](../examples/runs/history/)，没有被覆盖。

## AI 生成内容的已知风险

- 合成数据和规则词表是 AI 编写的，覆盖面有限，不代表真实的合规标准。
- 系统提示词中的业务策略（例如“替代时段默认不早于原要求”“争同一时段时优先调整有窗口的素材”）是 AI 根据题意提出的假设，需要业务方确认。
- 第 2 轮之后，在提示词里加了一条通用的冲突处理策略。这条规则没有提到具体素材，但它是在看到 09 场景失败之后加的，存在“针对测试调提示词”的风险。为此用重复回放来衡量稳定性，而不是只展示一次成功的运行。

- 本轮定向复现表明，跨请求草稿的确认状态、复检结果和真实 I/O 故障还没有被现有测试完整约束，详见本轮 review；不能仅依据 47 个测试通过断言核心边界全部有效。
